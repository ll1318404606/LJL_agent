# RAG 系统深度解析

## RAG 是什么

RAG（Retrieval-Augmented Generation，检索增强生成）是一种将信息检索与大语言模型生成相结合的技术架构。它的核心思想是：在 LLM 回答问题之前，先从外部知识库中检索相关信息，将其作为上下文注入到 Prompt 中，让 LLM 基于这些"参考资料"生成回答。

## 为什么需要 RAG

大语言模型存在三个根本性局限：

### 知识截止日期
LLM 的训练数据有固定截止时间。例如 GPT-4 的知识截止于 2023 年底，无法回答关于 2024 年事件的问题。

### 幻觉问题
当 LLM 缺少相关知识时，它不会说"我不知道"，而是会"编造"一个听起来合理的答案。这在医疗、法律、金融等高风险场景是不可接受的。

### 领域知识缺失
通用 LLM 不了解企业内部文档、专有数据、特定领域的专业知识。而这些往往是企业应用中最有价值的知识。

RAG 同时解决这三个问题：知识可以是实时的（更新知识库即可）、幻觉大幅减少（有据可查）、领域知识完整（用企业内部文档建库）。

## RAG 的核心流程

### 离线阶段：知识库构建

第一步是**文档收集**。将企业内部的 PDF、Word 文档、Wiki 页面、代码仓库、会议记录等全部收集起来。

第二步是**文档解析**。Word 的 `.docx` 不是纯文本，PDF 可能是扫描版，需要 OCR。这一步的目的是从各种格式中提取纯文本内容。

第三步是**文本分块**（Chunking）。长文档不能整篇塞进向量库——检索时需要精准定位到具体段落。分块的策略直接影响 RAG 效果：

- **按固定长度切**：最简单，每 N 个字符或 Token 切一刀，设置 overlap 保证语义连续性
- **按段落切**：尊重文档的自然结构，一个段落一个块
- **按语义切**：用模型判断语义边界，成本高但效果最好
- **按标题切**：Markdown 等结构化文档按 H1/H2/H3 切，层次清晰

第四步是**向量化**。用 Embedding 模型将每个文本块转换为一个高维向量（通常 384~1536 维）。语义相近的文本，它们的向量在空间中距离也相近。常用模型：OpenAI text-embedding-3、BGE、Sentence-BERT。

第五步是**建索引**。将所有向量存入向量数据库（如 ChromaDB、Milvus、Pinecone），并建立 ANN（近似最近邻）索引以加速检索。

### 在线阶段：问答流程

1. 用户提问："MCP 协议如何做工具发现？"
2. 问题向量化：用同一个 Embedding 模型将问题转为向量
3. 相似度检索：在向量库中找到 Top-K 个最相似的文本块
4. 上下文拼接：将检索到的文本块和原始问题拼成增强 Prompt
5. LLM 生成：LLM 基于这些"参考资料"生成回答

## 检索质量优化

### 混合检索
纯向量检索擅长语义匹配，但在精确关键词（如错误码、API 名称）上表现不如传统全文检索 BM25。混合检索将两者结果加权融合，取长补短。

### 重排序（Re-Ranking）
初始检索召回 Top-20 个候选，用一个更精确但更慢的 Cross-Encoder 模型对它重新排序，只保留 Top-5 给 LLM。这兼顾了速度（ANN 快速召回）和精度（Cross-Encoder 精准排序）。

### 查询改写
用户的问题往往不是最优的检索查询。可以用 LLM 先改写问题——比如把口语化问题改成检索关键词、把一个复杂问题拆成多个子问题分别检索。

### HyDE（假设性文档嵌入）
让 LLM 先根据问题生成一个"假设性答案"，然后用这个假设答案去检索。因为假设答案和真实文档在语言风格、用词上更接近，检索命中率往往高于直接用问题检索。

## 分块策略深度对比

| 策略 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 固定 Token 数（256/512） | 简单可控，Token 计算精准 | 语义被截断 | 对延迟敏感的实时应用 |
| 固定字符数（~500字） | 实现简单 | 中文一个字符≠一个 Token | 快速原型 |
| 按段落 | 语义完整 | 段落长度差异大 | 通用文档、文章 |
| 按标题层级 | 层次清晰，检索可按章节 | 标题级内容可能过多 | 技术文档、手册 |
| 按句子+上下文窗口 | 检索粒度细，精度高 | 块数量大，存储多 | 法律文书、合同 |
| 语义分块 | 语义边界最准确 | 需额外模型，速度慢 | 高质量需求 |
| 代码 AST 分块 | 保护代码结构 | 语言相关，实现复杂 | 代码仓库 |

实际项目中常用**组合策略**：先按标题切大段，大段内按段落切小块，小块合并到 500~800 字符。

## 向量数据库选型

### ChromaDB
轻量级，Python 原生，适合原型和中小规模。支持持久化，自带 Embedding 集成。

### Milvus
分布式向量数据库，支持十亿级向量，云原生架构。性能强大但运维复杂。

### Qdrant
Rust 编写，高性能。提供 Filter + Vector 混合查询，支持多语言客户端。

### Pinecone
全托管云服务，免运维，按量付费。适合不想管理基础设施的团队。

## 评估体系

RAG 系统需要从两个维度评估：

**检索质量**：用 Hit Rate、MRR、Recall@K 等指标衡量检索模块是否找到了正确的内容。

**生成质量**：用 Faithfulness（忠实度）、Answer Relevance（答案相关性）、Context Precision（上下文精确度）等指标衡量 LLM 是否基于检索内容生成了正确回答。

常用评估框架：RAGAS，TruLens。

## 常见陷阱

1. **分块过大**：检索到的块包含太多无关内容，稀释关键信息，浪费 Token
2. **分块过小**：缺少上下文，LLM 看不懂片段在说什么
3. **Overlap 过大**：不同块内容高度重复，浪费存储和检索带宽
4. **Embedding 模型不匹配**：用英文模型处理中文，或用通用模型处理代码
5. **忽视元数据过滤**：只靠向量相似度，不用时间/类别/来源过滤，召回一堆过时或不相关的内容
